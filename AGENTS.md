## anki-english-app

Single-flow app (no auth, no database) that turns an Anki deck into an AI-generated dialogue, then a real-time spoken-practice session. All persistence is `localStorage` — there is no backend datastore. Flow: `/` (deck picker) → `/deck/[deckName]` (dialogue generation) → `/practice?id=...` (voice practice).

## Where things are

- Vocabulary loading: `lib/vocabulary/` — `types.ts` holds the neutral, transport-free `VocabularyItem` / `VocabularyCollection` types **and** the `VocabularySource` contract (import these, never source-specific ones); `source.ts` holds only the registry (`getVocabularySource()`, defaults to Anki) and re-exports the interface; `sources/anki.ts` is the one concrete implementation; `setup-hint.ts` parses a source's connection-help steps (`**bold**`, `` `code` ``) into React-free segments. Anki internals (`AnkiCard`, HTTP calls, field parsing) are module-private — add a new source as a sibling under `sources/`, don't widen the Anki module's exports. Extraction in `sources/anki.ts` is content-driven, not note-type-driven: clean the `Front` (strip `[sound:…]`, `[…]` IPA groups, trailing POS markers, edge quotes/ellipsis/terminal punctuation) and use it if it is usable English — non-empty, ≤ 80 chars, no interior ellipsis/`__` blank, no Vietnamese-specific letter; otherwise fall back to the first *usable* `<b>`/`<strong>` in `Back` (BBC-Reactor shape), meaning = rest of Back else stripped Front; otherwise drop the card. Items are deduped by word, case-insensitively. Its `VIETNAMESE_LETTERS` is deliberately *narrower* than the validator's (plain French-style accents excluded so `café` survives) — keep the two copies independent. Concrete sources import the interface from `types.ts`, never from `source.ts`, so the registry stays a leaf.
- Anki access goes through `app/api/anki/route.ts` — never call `http://127.0.0.1:8765` (AnkiConnect) directly from client code, it has no CORS headers.
- Dialogue script: `lib/dialogue/` — `types.ts` holds the transport-free `DialogueScript` (`version: 3`, a list of turns each with `speaker: "system" | "learner"`, `text`, its own `targetWords`, and — on `learner` turns only — `hints`) plus the shared constraint constants (`MIN_TURNS`, `MAX_TARGET_WORDS_PER_TURN`, `MAX_EXTRA_HINT_KEYWORDS`, `MIN_LEAKED_CONTENT_WORDS`, …); `validate.ts` holds `validateScript(script, requestedWords)`, the **single definition of a valid script**, and the `isDialogueScript` shape guard. Change a rule there, not in the prompt — and when a rule has a number, interpolate the constant into the prompt so the model is told the rule that is actually enforced.
- `words.ts` owns whole-word matching and safe rendering: `containsWord` and `renderHighlightedHtml(text, words)`. Target words are carried as data — never recover them by substring search (`cold` matches inside `colder`). Every `dangerouslySetInnerHTML` site fed model or user text must go through `renderHighlightedHtml` (or `escapeHtml`): it highlights on raw text and escapes per segment, so escaping can neither break a match nor be broken by one. Don't reintroduce `highlightWords(escapeHtml(x))` — that order corrupts entities. `lib/gemini.ts`'s older `highlightWords` survives only inside `DialogueDisplay`'s legacy branch.
- Hint ladder (`DialogueHints`): two rungs in fixed order — `situation` (level 1, **Vietnamese**: when the line is used, never a translation of it) and `keywords` (level 2: the turn's own target words plus at most `MAX_EXTRA_HINT_KEYWORDS` other content words, every one of them a word from that line). There is deliberately no third rung and no level may reveal the whole line. Hints are generated in the **same** Gemini call as the script and stored with it — opening one must never cost a network request, so never add a hint-fetching endpoint. Only `learner` turns carry them, and the route strips stray ones before responding. `hasHints(script)` / `turnHasHints(turn)` report a ladder a learner could actually open — presence alone is not enough, since the accept-with-faulty-hints path can ship an empty one. `stopwords.ts` (English function words, `contentWords`, `containsSequence`) is what makes "at most 2 other content words" and "borrows ≥`MIN_LEAKED_CONTENT_WORDS` of the line's content words in a row" checkable; it is a *sequence* view of text and is not a second word-boundary matcher — `words.ts` still owns target-word matching. Pass the turn's target words as `alwaysContent` wherever it is called: the list contains words an A2/B1 deck teaches as vocabulary (`like`, `right`, `well`), and a target word must never be treated as glue.
- Script versions: 1 = the pre-Story-1.2 markdown string (`HistoryEntry.legacyDialogue`, never a `DialogueScript`), 2 = structured, no hints, 3 = with hints. `isDialogueScript` accepts **every** version in `SUPPORTED_SCRIPT_VERSIONS` so older stored entries keep loading; `validateScript` insists on the current one, because only fresh model output has to be current. When bumping the version, extend the array in the same commit — `types.test.ts` pins that `DIALOGUE_SCRIPT_VERSION` is a member, and breaking it makes every newly saved entry unreadable. A v2 entry is read as-is and **never upgraded in place**: nothing rewrites stored scripts, so v2 entries simply have no hints forever. Consumers must treat `hints` as optional.
- Dialogue generation: `lib/gemini.ts` + `app/api/dialogue/route.ts`. The route asks Gemini for JSON against a `responseSchema`, assigns each turn's `index` from array position, validates, and on a violation retries **exactly once** on the same model with the violations fed back, then returns 422. Model fallback is for transport failures only — a validation failure means the model understood and got it wrong. Only a *validated* rejection may produce a 422; a transport failure on the repair call is a 500. `validateScript` reports its findings in **three separate arrays**: fatal `violations`, `hintViolations`, and non-fatal `softViolations` (today only the consonant-clash rule). All three are fed to the one repair attempt, but only fatal `violations` can cost the user a generation — hint and soft faults never can. Concretely, both attempts stay on the table and the route returns the **better of the two**: any fatal-clean attempt beats none (fewer hint+soft faults wins, ties keep the earlier), and a 422 is only possible when *neither* attempt was fatal-clean; its `violations` body is fatal-only. So a repair that transport-fails, or that regresses and breaks a fatal rule, cannot throw away a first attempt whose script was already valid. Keep the three arrays apart; don't merge them, and don't reduce the decision to "look at the last attempt". The `violations` array in a 422 body is diagnostic — English, model-facing — and must never be shown to the user; the Vietnamese `error` string is the user-facing text.
- Voice practice: `hooks/useGeminiLive.ts` + `public/audio-processor.worklet.js`.
- Native sample audio: `app/api/tts/route.ts` (Azure TTS **proxy**) + `lib/sample-audio.ts` (decisions) + `hooks/useSampleAudio.ts` (transport and React state) + a play control per turn in `DialogueDisplay.tsx`. Every line of **both** roles gets audio, generated **once** and kept: `SPEAKER_VOICES` in `lib/dialogue/types.ts` gives the two roles two *distinct* en-US neural voices (one voice reading both parts removes the only cue that separates them by ear), and the blob is keyed by `sha256(voice + " " + text)` — content, not `HistoryEntry.id`, because audio is generated before the user clicks save and there is no id yet. Content keys make duplicate lines share one blob for free and keep the same line on the other role separate. Generation runs in the **background** (the script must be readable immediately) and **sequentially** (the free Azure F0 tier is rate-limited) — don't parallelise it, and note that a module-level in-flight map in `sample-audio.ts` shares one synthesis between concurrent callers so a React StrictMode double-mount doesn't buy the first line twice. It is driven **solely** from `DialogueDisplay`, and nothing resumes it: navigating away mid-run leaves the remaining lines unsynthesised until that script is shown again. Three failure modes, deliberately different — a per-line fetch failure (timeout, 502) marks that turn `failed` and the loop continues, because one bad line must not cost the other eleven; a *provider* failure (`/api/tts` 503 or 401 — no credential or a rejected one) and a *write* failure both stop the loop and produce **one** Vietnamese notice, because both are true of every remaining line. Whenever the loop stops early, the turns it never reached are marked `failed` rather than left `idle` — `idle` means "still queued" and a control stuck there forever promises audio that is not coming. None of it ever costs the user the script.
- Binary storage: `lib/blob-store.ts` — IndexedDB (`ankichat_blobs`), the app's *second* persistence layer, namespaced (`putBlob`/`getBlob`/`hasBlob`/`deleteBlob`/`deleteNamespace`, keys are `blobId(namespace, key)` = `${namespace}:${key}` — every operation goes through it, and `blob-store.test.ts` pins that they agree, because dropping the namespace from one side alone makes `hasBlob` false forever and silently re-bills Azure on every reopen). Story 1.4 owns the `"tts"` namespace; **Epic 2 reuses this layer for the learner's own recordings** under its own namespace, so keep it general — don't fold TTS specifics into it. Audio never goes in `localStorage`: `lib/history.ts` stays the text layer, and `historyStorage.clear()` drops the whole `"tts"` namespace with it (fire-and-forget) so blobs don't outlive every entry they belonged to. Cleanup is deliberately all-or-nothing: blobs are content-keyed and **shared** between entries, so deleting one entry's keys can mute another entry's lines — don't add per-entry cleanup without solving that first. `vitest` runs in `environment: "node"` and there is **no IndexedDB in tests**, which is why `lib/sample-audio.ts` is IndexedDB-free and takes a `SampleAudioStore` parameter — the claims worth testing (a reopened script fetches nothing, content-key identity and voice separation, quota handling) live there and are covered; `blob-store.ts` itself is the thin hand-verified wrapper. Don't add `fake-indexeddb` to move that line.
- History/persistence: `lib/history.ts` — the only persistence layer in the app. `HistoryEntry.script` is the structured script, v2 or v3 alike; entries written before Story 1.2 stored one markdown string and normalize on read to `script: null` + `legacyDialogue`. Consumers branch on `script` and fall back to `legacyDialogue`. In practice a legacy entry only ever reaches `VoicePractice.tsx` (via `/practice?id=…`); `DialogueDisplay.tsx` also keeps a legacy markdown branch, but nothing currently routes an old entry into it — it is retained-but-unreachable, so don't delete it and don't assume it is exercised either. `getAll()` skips stored elements that aren't presentable as entries and strips malformed `hints` via `withoutMalformedHints` before the shape guard runs — a garbled ladder costs the entry its hints, never its script; `readRaw` stays raw so mutators never rewrite what is already in `localStorage`.

## Running and verifying

- Tests run with Vitest: `npm test` (`vitest run`, config in `vitest.config.mts` — the `.mts` extension is deliberate, `.ts` triggers a Vite `configLoader` deprecation warning). Specs are `*.test.ts` next to the code, under `lib/`, `app/`, `components/`, or `hooks/`. Coverage is thin and node-environment only — there is no jsdom, so no component or E2E testing setup; a `.test.tsx` will be collected and then fail for want of a DOM.
- `npm run lint` is **not** clean and isn't expected to be: 3 pre-existing `react-hooks/set-state-in-effect` errors at `app/page.tsx:15`, `app/practice/page.tsx:18`, `components/HistoryPanel.tsx:19`, plus assorted unused-var warnings. They predate the vocabulary-source refactor — don't go chasing them as if you broke something. `npx tsc --noEmit` and `npm run build` are clean, and should stay that way.
- Anki Desktop + the AnkiConnect add-on must be running locally on port 8765 for anything past the landing page to work; there's no way to tell this from the code alone.
- `GEMINI_API_KEY` must be set in `.env.local`; the literal placeholder `"your_gemini_api_key_here"` is treated as "not configured" by app code.
- `AZURE_SPEECH_KEY` / `AZURE_SPEECH_REGION` must be set in `.env.local` for sample audio (`/api/tts`) and pronunciation assessment (`/api/pronunciation`) — one key, one bill, two endpoints. Missing either one is a 503 carrying the same Vietnamese message from `/api/tts` and from the pronunciation route's **azure branch** (that route also has a gemini branch with its own message); a key Azure *rejects* is a 401 from `/api/tts`. The client treats both as whole-script conditions and stops generating after one. The script still renders, it just has no audio.

## Conventions that differ from defaults

- Styling is inline `style={{}}` plus global utility classes in `app/globals.css` — `tailwindcss` is a dependency but unused in components; don't introduce Tailwind classes.
- UI copy is in Vietnamese — keep new user-facing strings consistent with that.
- `app/api/anki/route.ts` enforces a hardcoded `ALLOWED_ACTIONS` whitelist (read-only) on AnkiConnect calls — extend it deliberately, never remove or bypass the check.
- `app/api/dialogue/route.ts` falls through a hardcoded list of Gemini model names on failure/quota errors — when changing models, edit the `models` array there, not the `ai`/`@ai-sdk/google` SDK deps (they're installed but unused; the route calls the Gemini REST endpoint directly). `thinkingConfig: { thinkingBudget: 128 }` is deliberate — `0` is rejected with a 400 by some 3.x models, and omitting it lets hidden reasoning eat `maxOutputTokens`.

## Known pitfalls

- `app/api/live-token/route.ts` returns the raw `GEMINI_API_KEY` to the browser — deliberate dev-only shortcut, not a bug to "fix"; production would need ephemeral tokens instead. It is **not** a pattern to copy: `app/api/tts/route.ts` proxies Azure precisely so `AZURE_SPEECH_KEY` never reaches the client, and its error paths redact the key out of anything Azure echoes back. Any new provider route proxies.
- `/api/tts` builds SSML, which is XML — model text goes through the route's own XML escape, **not** `escapeHtml` from `lib/dialogue/words.ts` (that one leaves `"` and `'` alone, which is fine for a text node and wrong near an attribute). It also strips what XML cannot carry at all — control characters, lone surrogates, U+FFFE/U+FFFF — since no entity makes those legal and a lone surrogate breaks the request's own UTF-8. The voice name is checked against `ALLOWED_VOICES` rather than escaped, the same closed-set reflex as `ALLOWED_ACTIONS` in the Anki route; `ALLOWED_VOICES` is written out **independently** of `SPEAKER_VOICES` (not derived from it) so the test that they agree can actually fail — same two-declarations-one-test shape as `DIALOGUE_SCRIPT_VERSION` / `SUPPORTED_SCRIPT_VERSIONS`. `text` is length-capped too: it is the field Azure bills per character. Both sides of the proxy set a timeout (server 15s, client 20s so the server's message wins), because a hung connection would otherwise stall the sequential loop forever with no error and no notice.
- If AnkiConnect isn't running, deck loading fails with a Vietnamese connection-error message that can look like a UI bug rather than a missing dependency.
